## 为什么不能用当前源码直接校验全部旧包

`43bc3af` 修改了事件日期规范化、理解解析器和 provider；后续类型修正改变了 v2 sender 的源码字节。旧包拒绝这些源码指纹是正确行为，不能更新旧 hash、关闭检查或覆盖旧报告来获得绿色结果。

`source-map.json` 给出四份旧源码的 SHA256、来源与快照位置：

- 三份业务源码取自 `d17f3f9`，逐字节匹配旧包引用。
- v2 sender 取自类型修正前快照，逐字节匹配已冻结授权；修正仅增加 `as const`，转译后的 JavaScript 不变。
- 快照使用 `.snapshot` 后缀，不进入 TypeScript 编译或测试发现，也不替换当前业务源码。

## 隔离复核

1. 用 `git archive HEAD` 导出到新临时目录，仅为该副本链接现有 `node_modules`，不要复制 `.env`、业务数据库或 `.git`。
2. 在副本内读取 `source-map.json`，先验证每份快照 SHA256，再将其恢复到对应相对路径。**绝不在工作树执行恢复。**
3. 在该副本使用各阶段 README 中的 `--verify` 与原信任锚，仅从冻结文件重建结果，不使用 `--out` 或 `--send`。
4. v1 应复现原有不可评分状态（CLI exit 2），v2 应复现原有开发集评分；Bridge、Admission、Blind 应重建原结果。历史副本不是当前业务版本，不能用于宣称当前类型检查或生产效果通过。

`tests/helpers/historical-evaluation-repo.ts` 为单测按 manifest 的直接依赖建立独立夹具，验证快照后恢复旧源码；真实工作树保持不变。新增回归同时确认当前源码仍拒绝旧 Bridge 指纹。没有 mock 掉完整性校验。
